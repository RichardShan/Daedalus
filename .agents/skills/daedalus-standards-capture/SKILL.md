# 规范沉淀

> 规范是活文档。每次调试、每个「原来如此」的时刻，都是让实现契约更清晰的机会。

## 什么时候更新

| 触发 | 目标 |
|------|------|
| 实现了一个功能 | 记录设计决策和接口契约 |
| 修了一个 bug | 记录常见错误和预防方法 |
| 发现了一个模式 | 记录为推荐模式 |
| 踩了一个坑 | 记录为注意事项 |
| 确立了一个惯例 | 记录为项目约定 |

## 放哪里

```
.daedalus/spec/
├── <layer>/        # 编码规范（怎么写代码）
│   ├── index.md
│   └── *.md
└── guides/         # 思考清单（写代码前想什么）
    ├── index.md
    └── *.md
```

**判断标准：**
- 「这是**怎么写**代码」→ 放 `<layer>/` 目录
- 「这是**写代码前该想到什么**」→ 放 `guides/`

## 怎么写

1. **读现有规范** — 避免重复，找到正确的位置
2. **写具体内容** — 包含代码示例、文件路径、实际值
3. **解释原因** — 说清楚这个规则防止什么问题
4. **更新索引** — 如果新增了文件或章节

### 触发深度规范的条件

当改动涉及以下任一项时，必须写完整的 7 段式规范：

- 新增/变更 API 签名
- 跨层契约变更
- 数据库 schema 变更
- 基础设施集成

**7 段：** 范围/触发 → 签名 → 契约 → 校验与错误矩阵 → 好/基/坏案例 → 需要的测试 → 错误 vs 正确

### 一般规范格式

```markdown
### 规则名称

**场景**: 什么时候适用
**做法**: 本项目的模式 + 参考文件路径
**常见错误**: 容易踩的坑
**验证**: 怎么确认遵守了这个规则
```

## 质量检查

- [ ] 内容具体可操作？
- [ ] 包含代码示例？
- [ ] 解释了为什么而非只说了是什么？
- [ ] 没有与现有内容重复？
