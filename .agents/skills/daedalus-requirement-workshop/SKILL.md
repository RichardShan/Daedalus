# 需求工坊

## 铁律

1. **代码优先** — 能从代码库找到答案的问题，不要问用户。先读代码、测试、配置、文档，再提问。
2. **逐个提问** — 每次只问一个问题，附上你的推荐答案和权衡分析。
3. **只问决策** — 用户需要回答的只有：产品意图、优先级、范围边界、风险容忍度。

## 工作流

1. 捕获用户需求，写入需求文档初稿。
2. 探索代码库收集证据，分离出：
   - 已确认的事实
   - 需要用户确认的产品意图
   - 需要用户决策的范围/风险问题
   - 大概率不在范围内的内容
3. 问最有价值的一个问题（附推荐答案）。
4. 用户回答后，更新需求文档再继续。
5. 复杂任务需补充设计文档和实现计划。
6. 结束前执行收敛检查。

## 问题格式

每个问题必须包含：
- 需要决策什么
- 为什么这个决策重要
- 你的推荐答案
- 选择其他方案的代价

## 思考框架：回到第一性原理

当需求模糊或方案感觉过度工程化时：

1. **重新描述问题** — 去掉实现细节，用一句话说要解决什么
2. **列出基本事实** — 什么是不以人的意志为转移的约束？
3. **质疑假设** — 「我们一直用 X」不是理由。如果去掉 X 什么都不会坏，那 X 是不必要的
4. **从事实出发重建** — 最小可行方案是什么？每增加一个复杂度都要说明是哪个基本事实要求的

## 收敛检查

完成前检验：
- [ ] 需求文档包含可测试的验收标准
- [ ] 无重复事实跨节出现
- [ ] 代码库能回答的问题已通过探索解答
- [ ] 剩余开放问题确实是用户意图或范围问题
- [ ] 复杂任务有设计文档和实现计划
- [ ] 用户已审阅或明确同意继续

在用户批准前不开始实现。
