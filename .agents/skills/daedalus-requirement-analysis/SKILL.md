# 需求澄清

## 步骤

1. **明确目标** — 用户要解决什么问题？谁受益？成功是什么样子？
2. **划定边界** — 什么在范围内，什么明确不做。标记容易被误认为需求的「非目标」。
3. **提取场景** — 主要路径 + 边界条件 + 异常路径。每个场景用一句话描述触发条件和预期结果。
4. **定义验收标准** — 把模糊描述转为可验证的条件。可验证 = 能用代码、测试或命令确认 true/false。
5. **标记待定项** — 假设、依赖、风险、必须由用户决策的问题。每项注明阻塞程度（可先行开发 / 必须先确认）。
6. **输出需求摘要** — 在编码前将以上内容整理为结构化文档。

## 输出格式

```markdown
## 目标
<一句话描述要解决的问题>

## 用户场景
- [主路径] ...
- [边界] ...
- [异常] ...

## 验收标准
- [ ] <可验证的条件>

## 非目标
- ...

## 待确认
- [阻塞] ...
- [可先行] ...
```

## 注意

- 先检查代码库中已有的相关实现和文档，再向用户提问。
- 避免复述用户原话 — 用更精确的语言重新组织。
- 验收标准不是功能列表 — 是判断「做完没做完」的客观条件。
