# 根因分析

> 调试的价值不在修复 bug，在于让这类 bug 不再出现。

## 分析框架

### 1. 根因分类

| 类别 | 特征 | 示例 |
|------|------|------|
| **A. 缺少规范** | 没有文档说明该怎么做 | 新功能没有检查清单 |
| **B. 跨层契约不清** | 层间接口不明确 | API 返回格式与前端期望不符 |
| **C. 变更传播遗漏** | 改了一处漏了其他 | 改函数签名但漏了调用方 |
| **D. 测试覆盖缺口** | 单测过但集成挂了 | 单独跑正常，组合起来崩溃 |
| **E. 隐式假设** | 代码依赖未文档化的假设 | 时间戳秒 vs 毫秒 |

### 2. 修复为什么失败（如果尝试了多次）

每次失败的原因：表层修复 / 范围不完整 / 工具局限 / 心智模型错误

### 3. 预防机制

| 类型 | 手段 |
|------|------|
| 文档 | 更新规范让后来者知道 |
| 架构 | 让错误在结构上不可能 |
| 编译期 | 类型约束、签名检查 |
| 运行时 | 监控、告警 |
| 测试 | 集成测试、E2E |

### 4. 系统性扩展

- 还有哪些地方可能存在同类问题？
- 暴露了什么设计缺陷？
- 开发流程有什么可改进的？

### 5. 知识沉淀

**分析完成后必须立即执行：**

- 更新 `.daedalus/spec/guides/` 或相关规范文档
- 不要只列 TODO — 直接改文件

> 分析如果只留在对话里就毫无价值。价值在于更新后的规范。

## 思考方法

面对多个可能的根因时：

1. 先列出假设和初始信心度
2. 收集证据，根据证据更新信心度
3. 不要重复收集同类证据 — 找能**区分**假设的证据
4. 信心 <70% 时先验证假设再提交修复
5. 警惕确认偏误 — 主动寻找**反对**当前假设的证据
